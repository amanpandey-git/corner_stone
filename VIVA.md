# VIVA - likely examiner questions

Each step adds 3-5 questions with short answers when it finishes.

## Step 0 - Setup & architecture
- **Q: Why write ARCHITECTURE.md before code?** A: Contracts (inputs, outputs, errors) are agreed first, so modules can be built and tested independently and Stage 2 can plug in without rewrites.
- **Q: Why HNSW instead of a flat index?** A: A flat index compares the query with every vector (O(N)). HNSW walks a layered proximity graph and visits only a small fraction (roughly O(log N)), trading a little recall for large speed-ups as the corpus grows.
- **Q: hnswlib vs faiss?** A: Same algorithm. hnswlib has no Windows wheel and needs a C++ compiler, so I used faiss `IndexHNSWFlat` behind my own interface; the rest of the code does not know which backend is used.
- **Q: Why a manifest file next to the index?** A: Vectors from different models are not comparable. The manifest records model, dimension, space and normalisation, and loading refuses a mismatch instead of silently returning garbage.

## Step 1 - Extraction
- **Q: How do you detect a scanned page?** A: Almost no extractable text (< 25 chars) while the page contains an image. It is flagged `needs_ocr` with a reason and counted; text is kept for Stage 2 OCR. A page with no text and no image is flagged `empty`.
- **Q: How are headings found in a PDF?** A: PDFs have no heading tags, so I compare font sizes: body size is the size carrying most characters in the document; lines at >= 1.15x that are short are headings, ranked into levels by size.
- **Q: Why PyMuPDF?** A: Fast, pure wheels on Windows, gives per-span font size and image blocks, which I need for headings and scan detection.
- **Q: Why remove headers/footers, and how?** A: A repeated footer ("Dr X, MITS-DU") would be embedded into every chunk and pollute similarity. I count lines (digits/punctuation ignored) at the top/bottom of each page and remove those appearing on at least half the pages.
- **Q: Why NFC and not NFKC normalisation?** A: NFKC rewrites symbols (e.g. superscripts, some maths characters); NFC keeps them. Ligatures are expanded explicitly instead.
- **Q: Why does DOCX have no page numbers?** A: Page breaks in DOCX depend on rendering (fonts, printer), so a page number would be invented. I store heading sections with paragraph ranges, which are stable.

## Step 2 - Chunking
- **Q: Why chunk at all, and why 256 tokens with 48 overlap?** A: The embedding model reads up to 512 tokens and one vector per chunk must represent one idea; 256 is about 1-2 paragraphs, so a hit points to a precise page. Overlap (~19%) makes sure a sentence cut by a boundary is complete in at least one chunk.
- **Q: What is structure-aware chunking?** A: I split at headings first (so a chunk never mixes two topics), and only then by token windows inside long sections. A heading line stays at the top of its chunk so the topic words are embedded with the content.
- **Q: What if a section or sentence is longer than the model limit?** A: It is split (by sentence, then by words), never truncated; hard_max is 480 < 512. A test with a 400-word unpunctuated sentence proves nothing is lost.
- **Q: What happens to tiny fragments like a lone heading?** A: Under 40 tokens they are merged into the next chunk, otherwise they would be retrieved as meaningless hits.
- **Q: Why count tokens with the model tokenizer, not words?** A: The limit that matters is in model tokens (WordPiece splits rare words into pieces); words under-count.
## Step 3 - Embeddings
- **Q: What is the bge query prefix and why only on queries?** A: bge-small-en-v1.5 was trained with the instruction "Represent this sentence for searching relevant passages: " in front of short search queries, so a question lands close to the passages that answer it. Passages are documents, not questions, so they get no prefix. The prefix is part of the model contract, so it lives in config.yaml and is tested.
- **Q: Why normalise vectors to unit length?** A: With unit vectors, cosine similarity equals the plain inner product, which is what the index computes fastest; it also removes length effects so only direction (meaning) matters, and scores fall in a fixed -1..1 range that can be compared across queries.
- **Q: Why bge-small-en-v1.5 and not a bigger model?** A: 33M parameters (about 130 MB), 384 dimensions, strong English retrieval for its size, and it runs on 4 CPU cores in 8 GB RAM. Bigger models would be slower with little gain on a few hundred chunks.
- **Q: How do you embed 300+ pages without running out of memory?** A: Chunks are encoded in batches of 32; only the small (n x 384 float32) result matrix is kept, so memory is bounded by the batch, not the document.
- **Q: How do you know the embeddings are sensible?** A: Tests check dimension 384, unit norm, that a deadlock question scores higher against a deadlock passage than a bread recipe, and that batched and single encoding agree.
## Step 4 - Index + store
- **Q: What do M, ef_construction and ef_search control?** A: M is how many links each node keeps in the graph (more links = better recall, more memory). ef_construction is how wide the search is while building (better graph, slower build). ef_search is how many candidates are explored per query (higher = better recall, slower query); it must be at least k, so I use max(ef_search, k).
- **Q: Why IndexIDMap2 and add_with_ids?** A: HNSW numbers vectors 0,1,2... by insertion. The wrapper lets me give each vector its chunk_id as label, so a search result is directly a SQLite primary key; no separate lookup table to keep in sync.
- **Q: How do you delete a document if HNSW cannot remove vectors?** A: Soft delete: SQLite marks the chunks deleted and search filters them out (over-fetching so k live results remain). Labels are never reused (AUTOINCREMENT), so a stale vector can never be confused with a new chunk.
- **Q: What does the manifest protect against?** A: Opening an index built with another model, dimension or metric. Vectors from different models live in different spaces, so results would be silently meaningless. The manifest records model name+revision, dimension, space and normalisation, and load raises ModelMismatch if any differs or the manifest is missing.
- **Q: Why a unit-norm check in add()?** A: The index uses inner product as cosine. A non-normalised vector would silently rank by length instead of meaning, so it is rejected.
- **Q: Why can a crash not leave a half-ingested document searchable?** A: Writes happen in one SQLite transaction and everything is first stored as `pending`; only a second transaction flips document and chunks to `active` together. Search only sees `active` chunks, so a crash leaves a pending document that `check_sync` reports and `discard_pending` cleans up.
- **Q: Why is the deleted flag in the chunks table?** A: One column (`chunks.status`) decides whether a vector may be returned, so search, stats and the sync check cannot disagree.
- **Q: How is "replace" kept safe?** A: `activate(new, replaces=old)` retires the old version and activates the new one in the same transaction, and a unique index allows only one active document per file name, so there is never a moment with two versions or none.
- **Q: Why AUTOINCREMENT?** A: Plain INTEGER PRIMARY KEY can reuse the id of a deleted row; AUTOINCREMENT never does, and those ids are index labels.

- **Q: Walk me through what happens when I upload a file.** A: SHA-256 of the bytes; if an active document has that hash it is skipped. Otherwise parse and clean, chunk, embed in batches, write SQLite rows as pending, add vectors to the index and save it, and only then activate the rows. Same name with new content retires the old version in the same transaction as the activation.
- **Q: Why activate only after the index file is saved?** A: Search trusts SQLite. If rows were active before the vectors were durable, a crash could leave chunks that search expects but the index cannot return.
- **Q: What happens to a corrupt or password-protected file?** A: The parser raises a specific error before anything is written; the report says `failed` with the error name and reason, and nothing needs cleanup.
- **Q: Why hash file bytes and not the file name?** A: A name can be reused with different content (replace) or a copy renamed with identical content (skip). Content identity is the hash.
- **Q: Numbers?** A: 7 PDFs, 422 pages, 409 with text, 13 flagged needs_ocr, 328 chunks, 38.7 s total on a 4-core laptop.

## Step 5 - Search + CLI
- **Q: How does search work end to end?** A: The query gets the bge prefix and is embedded to a unit vector; HNSW returns the nearest chunk ids by inner product; SQLite filters out anything not active and supplies file, page and section; results are ranked by score with a short snippet.
- **Q: Why over-fetch?** A: HNSW cannot delete, so retired chunks can sit among the nearest neighbours. I ask for 3k candidates, filter, and widen until k live hits exist, so replaced documents never appear and k is still filled.
- **Q: What does the score mean?** A: Cosine similarity between query and chunk (-1..1); 0.8+ is a strong match for bge on this data, but it is only a ranking, not a probability.
- **Q: Why does the CLI ask before discarding interrupted ingests?** A: Deleting state automatically could hide a real fault. The tool reports the problem, then discards only on explicit consent (`y` or `--yes`).
- **Q: Where could search be wrong?** A: Slide titles repeated across slides merge into one section (page ranges like 96-101), and some bullets are mistaken for headings; this affects citation precision, not whether the text is found.

## Step 6 - Verification
- **Q: How do you know the index returns the right results?** A: I compare HNSW with an exact numpy search over the same vectors: for each query, recall@10 is the share of the true top-10 that HNSW also returned. On the real index (328 vectors, 191 queries) it is 0.995 at ef_search=50 (0.952 at 10, 0.996 at 100); on a 10,000-vector synthetic scale check it is 1.000 at 50.
- **Q: Why is HNSW not faster than brute force in your demo?** A: With 328 vectors a single matrix product is as fast as walking a graph (0.026 ms vs 0.07 ms). The benefit appears with scale: at 10,000 vectors HNSW takes 0.11 ms against 0.82 ms exact, and the gap widens with size (exact is O(N), HNSW roughly O(log N)).
- **Q: What does ef_search trade off?** A: Recall for speed: ef 10 -> 100 raised recall 0.952 -> 0.996 on the real index and roughly doubled to tripled latency. I did not tune it on the evaluation questions; 50 is fixed in config.yaml and the sweep just reports it.
- **Q: What are the limits of this check?** A: It measures only whether HNSW approximates exact search; it says nothing about whether the right chunk is retrieved. That is the separate hit@5 / MRR evaluation on labelled questions. The 10,000-vector run is synthetic (perturbed real vectors) and labelled as such.
- **Q: What are hit@5 and MRR?** A: hit@5 is the share of questions for which a correct page is among the top 5 results; MRR is the average of 1/rank of the first correct result (1.0 if always first, 0.5 if second, 0 if not in the top 10). hit@5 says "is the answer in what the LLM would see", MRR says how high it ranks.
- **Q: What counts as a correct result?** A: A result from the labelled file whose chunk page range contains a labelled page. Chunks can span several slides, so a labelled page inside a range counts. For multi-page questions I also report how many labelled pages were found, separately.
- **Q: How do you avoid fooling yourself with the evaluation?** A: The scoring rules are fixed in the script before any results exist; the three questions I looked at in Step 5 are excluded; questions are validated (files and pages must exist) and written from the slides by the author; and chunking and ef_search are not changed after seeing the numbers.
- **Q: What is the weakness of 15-25 questions?** A: Small samples: one question moves hit@5 by 4-7 points, so the figure is indicative, not precise. I report counts next to the percentage and list every miss.

- **Q: What were your results?** A: On 20 questions written from the slides (3 of them spanning two consecutive pages), hit@5 = 0.95 (19/20), MRR = 0.885, and 5 of the 6 labelled pages of the multi-page questions were found in the top 5. Median end-to-end search time was 35 ms, p95 57 ms on a 4-core laptop CPU. ANN recall@10 against exact search was 0.995.
- **Q: Which question failed and why?** A: "Total seek time for FCFS with head at 50" (Unit 4). The answering chunk exists and is not flagged, so it is a ranking miss. The top 10 were five near-identical disk-scheduling slides, each appearing twice because that PDF repeats its own slides, so the effective depth was halved. I did not change anything after seeing this; it is documented as a limitation.
- **Q: Is 0.95 a reliable number?** A: It is indicative, not precise: 20 questions, so one miss is 5 points. The questions are written in a natural style and share some wording with slide titles, so this is an easier test than adversarial paraphrases. It shows the pipeline retrieves the right slide, not that it would on any question.

## Step 7 - Demo UI
- **Q: Why is there no logic in the Streamlit page?** A: The page only calls open_stack, ingest_file and search, the same functions the CLI and tests use, so what I verified is what the UI runs. It cannot disagree with the tested code.
- **Q: What went wrong when you first built the UI?** A: SQLite connections belong to the thread that opened them and Streamlit reruns the script on different threads, so a cached store crashed with ProgrammingError. I cache only the embedding model (slow to load) and open the store per run.
- **Q: How is the UI tested?** A: With Streamlit AppTest: page renders with stats, a search shows file/page/score, a blank query shows a message, and uploading a DOCX shows the ingestion report and then skipped_duplicate on a repeat.

## Step 8 - Wrap-up (evaluation and project-level questions)
- **Q: What does "zero silent failures" mean and how do you show it?** A: Every page ends up indexed or flagged with a reason, and every bad file produces a failed report. For the 7 PDFs: 409 pages with text + 13 flagged needs_ocr = 422 pages; the ingestion report prints each flagged page and its reason, and `stats` lists them.
- **Q: How did you build the evaluation set so it is not biased?** A: I wrote 20 questions from the extracted slide text, not from search results, with the answering phrase and page recorded in evidence.md. The scoring rules were fixed in the script before the first run, the three questions I had tried by hand are excluded, and I ran it once and changed nothing afterwards.
- **Q: Why hit@5 and MRR, and not accuracy?** A: Retrieval returns a ranked list, and the LLM stage will read the top few chunks. hit@5 says whether the right slide is among them; MRR also rewards ranking it first. There is no single "correct output" to take accuracy of.
- **Q: What is a failure in your evaluation and what caused it?** A: One of 20: the FCFS seek-time example in Unit 4. The chunk exists and is not flagged, so it is a ranking miss; the top 10 were five near-identical slides each appearing twice because that PDF repeats its own slides. I did not tune on it; it is listed as a limitation with candidate fixes (near-duplicate collapsing, better heading detection).
- **Q: What is `equivalent_pages` and was it a way of improving the score?** A: It lets a hit on a verbatim duplicate slide count, because the Unit 4 PDF contains its slides twice and either copy is correct. I added it before the first run, it affects only two questions, and it is logged; without it those two would be unfairly penalised for returning the identical copy.
- **Q: Is the 0.95 trustworthy?** A: It is indicative: 20 questions mean one question is 5 points, the wording is natural and shares words with slide titles, and all questions are single-file. The point is that the pipeline works end to end and that failures are inspectable, not that 0.95 would hold on any collection.
- **Q: ANN recall was 0.995. Does that mean retrieval is 99.5% correct?** A: No. It only says HNSW returns the same neighbours as an exhaustive scan would. Whether those neighbours answer the question is measured separately by hit@5 and MRR.
- **Q: What would break with a different collection?** A: Heading detection depends on font sizes; scanned documents need OCR; non-English text needs another embedding model (the manifest forces a re-index); documents with repeated content waste top-k slots.
- **Q: What would you do next?** A: Collapse near-duplicate chunks at search time, improve heading detection, add OCR for flagged pages, then build the generation stage (LLM answers with citations) on top of the same SearchResult objects.
- **Q: Why faiss instead of hnswlib, and does it matter?** A: hnswlib could not be built on Windows without a C++ compiler. faiss implements the same HNSW algorithm with the same M, efConstruction and efSearch; only deletion differs, which I handle with soft delete in SQLite. HNSW is not implemented from scratch because that was out of scope.
## Stage 2 Phase 0 - setup and evaluation design
- **Q: Why split the questions into dev and test?** A: If I tune chunking, fusion or the prompt while looking at the same questions I report, the number measures how well I fitted those questions, not how well the system works. Dev is for decisions; test is run only at fixed checkpoints and logged every time.
- **Q: Why are the 20 Stage 1 questions all in dev?** A: I already saw their results, and the one miss (Unit 4 duplicate slides) directly shaped the Phase 1 design. Using them as test would reward fixing a problem I knew about.
- **Q: What is a cross-file question and how is it scored?** A: One whose answer needs two decks, e.g. race conditions (Unit 1 p.17 and Unit 2 p.5). hit@5 counts if any labelled page is retrieved; separately I report how many have every file in the top 5, which is the harder, more honest number.
- **Q: Why have unanswerable questions in a retrieval evaluation?** A: They are not scored for retrieval; they are for Phase 2 abstention. Most are hard negatives (Belady's anomaly next to FIFO, copy-on-write next to fork) because those tempt an LLM to answer from general knowledge instead of saying "not in your notes".
- **Q: How do you know the labels are correct?** A: Each answer phrase was checked by a script to occur on its labelled page, each unanswerable key term to occur on no page, and the user spot-checks 10 against the PDFs.

## Stage 2 Phase 1 step 1 - schema v2, version check, rebuild
- **Q: Why does an old index fail instead of being upgraded automatically?** A: The v2 index needs data v0.1 never stored (units, duplicate pages, context headers, a keyword index), and its vectors will be computed from different text. A silent migration would mix old and new vectors. Failing with the exact rebuild command is honest, and rebuild keeps the old folder as a backup.
- **Q: Where is the version stored?** A: Twice: SQLite's `PRAGMA user_version` and `index_version` in manifest.json, because the database and the vector file can each be replaced on their own.
- **Q: What is FTS5 and why is it filled in the same transaction as the chunks?** A: SQLite's built-in full-text index (BM25 ranking). Writing its rows in the same transaction means a crash can never leave a chunk that keyword search cannot see, or a keyword hit with no chunk.
- **Q: What bug did rebuild expose?** A: The CLI never closed its database connection. A normal run exits so nobody noticed, but Windows refused to rename the folder during a second rebuild in the same process. Every command now closes the store.
## Stage 2 Phase 1 step 2 - near-duplicate pages
- **Q: How do you decide two slides are duplicates?** A: I turn each slide into its set of three-word sequences (shingles) and compute Jaccard overlap: shared shingles divided by all shingles. A later slide with overlap >= 0.95 to an earlier one is marked as its duplicate, recorded with the page it copies, and not indexed.
- **Q: Why shingles and not exact text comparison?** A: Extraction can differ by a stray space or line break between two copies of the same slide. Shingles tolerate that, but a changed word or number changes several shingles, so real differences still show.
- **Q: How did you choose 0.95?** A: It was fixed in the contract before measuring, then checked: true copies score about 1.0, the most similar different slides (SJF preemptive vs non-preemptive) score 0.92. There is a clear gap, and a test pins those numbers.
- **Q: Why keep digits and skip short slides?** A: Worked examples (FCFS vs SSTF seek time) share their wording and differ only in numbers. Short title or picture slides ("Practice Problem") share their few words but have different images, so they are never treated as duplicates.
- **Q: Did deduplication improve retrieval?** A: Only slightly on dev (MRR 0.816 -> 0.818; hit@5 unchanged). It frees result slots, but the remaining Unit 4 miss is caused by chunking across slides, which the next change addresses. I report that instead of claiming a fix.
## Stage 2 Phase 1 step 3 - page images
- **Q: Why render page images at ingest instead of when a citation is clicked?** A: Rendering once keeps the click instant and the UI simple (it just serves a file). The cost is disk space (49 MB for 422 slides) and about 40% more ingest time, measured.
- **Q: What happens if one page cannot be rendered?** A: That page gets no image and the report lists a warning; the text is still indexed. A test forces a render failure on one page to check this.
- **Q: Why store a relative path in SQLite?** A: So the data folder can be moved or rebuilt without rewriting every row; the image root comes from config.
## Stage 2 Phase 1 step 4 - slide-aware chunking and context header
- **Q: Why one chunk per slide?** A: A slide is the unit a student cites and looks at. One chunk per slide gives exact page numbers and stops consecutive slides with the same title being merged into one long section. On dev it raised hit@5 from 0.879 to 0.939.
- **Q: What is the context header and why embed it?** A: The line "file stem > section title" put before the slide text. Many slides only say "Advantages: ..." without naming the topic; embedding the header with the text tells the model what the slide is about.
- **Q: What happens to a slide longer than the model can take?** A: It is split into overlapping windows inside the same page, so nothing is truncated and every piece still cites that page.
- **Q: What about slides with almost no text?** A: A lone title or caption (under 15 tokens) joins the next slide, but only if it is the very next page; otherwise it stays alone. I first merged backwards too, and found a chunk citing p.26-33 across deleted duplicates, so I changed the rule and added a test.
- **Q: Did anything get worse?** A: Four dev questions moved from rank 1 to 2 or 3; all still hit. I report per-question changes, not only the average.
## Stage 2 Phase 1 step 5 - keyword search (FTS5)
- **Q: Why add keyword search when vector search already works?** A: Embeddings capture meaning but can blur exact rare terms such as "C-LOOK", "setuid" or "642". BM25 rewards exactly those rare words. On dev, keyword search alone was weaker (0.818 vs 0.939) but ranked four questions better than vector search, so combining them can help.
- **Q: What is BM25 in one sentence?** A: A relevance score that grows with how often a query word appears in a chunk, weighted by how rare the word is across all chunks (IDF), with a correction so long chunks are not favoured.
- **Q: How do you stop a question like `what is "NEAR*`? from breaking the SQL?** A: Every word is extracted and wrapped in double quotes before it reaches FTS5, so operators become plain words; the values are passed as SQL parameters, never pasted into the SQL string. A parametrised test feeds FTS syntax and an SQL-injection string.
- **Q: How is keyword search kept consistent with deletes?** A: It joins the chunks table and only returns `status = 'active'`, the same rule the vector side uses.
## Stage 2 Phase 1 step 6 - collapsing near-identical results
- **Q: You already remove duplicate slides at ingest; why collapse again at query time?** A: Ingest dedup only compares pages inside one document. If a student uploads two decks that share slides, both copies are indexed; collapsing at query time keeps one and lists the other location in `also_on`, so the top 5 is not wasted.
- **Q: Did it improve the numbers?** A: No: on dev not a single rank changed, because this corpus has no cross-file copies left. I kept it because it costs little (about 30 ms at p95 to gather 30 candidates) and protects against a real failure mode, and I report the zero gain honestly.
## Stage 2 Phase 1 step 7 - filters
- **Q: How does the unit filter work?** A: At ingest the unit ("Unit 4") is read from the file name with a regular expression in config. At search time the allowed document ids are looked up once in SQLite; vector hits from other documents are skipped and the over-fetch loop keeps widening until k allowed hits are found or the index is exhausted. Keyword search applies the same filter in its SQL join.
- **Q: Why filter after the vector search instead of building one index per unit?** A: One index keeps ingest, dedup and the version check simple. With a few hundred slides, over-fetching costs milliseconds; per-unit indexes would only pay off at a much larger scale.
## Stage 2 Phase 1 step 8 - compaction
- **Q: Why is compaction needed at all?** A: faiss HNSW cannot delete vectors, so replaced documents stay in the graph as soft-deleted entries that search must skip. Over time that wastes memory and over-fetch work. Compaction rebuilds the graph from the live vectors only and removes the dead rows.
- **Q: Where do the vectors come from without re-embedding?** A: IndexHNSWFlat stores the raw vectors, so they are read back (`reconstruct_n`) and only the active ones are added to a fresh graph. No model is needed.
- **Q: What if the program crashes halfway?** A: The new index is checked against SQLite and saved atomically before any row is deleted. A crash after the save leaves deleted rows without vectors, which the sync check already accepts, and the next compaction removes them. A test simulates exactly that crash.
- **Q: How do you delete from an FTS5 index that mirrors another table?** A: For an external-content FTS5 table you insert a special 'delete' command with the old row's values; deleting from the chunks table alone would leave stale keyword entries.
## Stage 2 Phase 1 step 9 - Reciprocal Rank Fusion and hybrid search

`rrf_merge` in `src/cornerstone/hybrid.py`, line by line:
- `def rrf_merge(rankings, k_rrf=60)`: it takes several ranked lists of chunk ids, best first (for me: the vector list and the keyword list), and the constant k.
- `scores: dict[int, float] = {}`: running total of the fused score for every chunk id seen in any list.
- `best: dict[int, int] = {}`: the best (smallest) rank each chunk got in any single list; only used to break ties.
- `for ranking in rankings:`: go through each retriever's list in turn.
- `for rank, cid in enumerate(ranking, start=1):`: walk down that list; `enumerate(..., start=1)` gives rank 1 to the top result, rank 2 to the next, and so on.
- `scores[cid] = scores.get(cid, 0.0) + 1.0 / (k_rrf + rank)`: add this list's contribution, 1 / (60 + rank). Rank 1 adds 1/61, rank 2 adds 1/62. A chunk found by both lists gets two contributions, so agreement is rewarded; a chunk missing from a list just gets nothing from it.
- `best[cid] = min(best.get(cid, rank), rank)`: remember the best position this chunk reached anywhere.
- `return sorted(scores.items(), key=lambda item: (-item[1], best[item[0]], item[0]))`: sort by score high to low (minus sign), then by best single rank, then by chunk id, so the order is always the same for the same input.
- Worked example (a test): vector [A, B, C], keyword [B, D, A]. B = 1/62 + 1/61 = 0.03252, A = 1/61 + 1/63 = 0.03227, D = 1/62 = 0.01613, C = 1/63 = 0.01587, so the order is B, A, D, C. B wins because both retrievers put it near the top.

- **Q: Why do you fuse ranks instead of the raw scores?** A: The two scores are on different scales. Cosine similarity from the embedding model is between -1 and 1 and in practice sits in a narrow band around 0.5 to 0.9, while BM25 is unbounded and depends on word rarity and chunk length. Adding them, or even normalising them, would let one retriever dominate by accident. Ranks are comparable: first is first in both lists. So I only use positions.
- **Q: Why k = 60?** A: 60 is the standard value from the original RRF paper (Cormack, Clarke and Buettcher, 2009), where it worked well across collections. It softens the gap between rank 1 and rank 2: 1/61 and 1/62 are almost equal, so a single list being very sure about its first result cannot outweigh two lists that both rank another chunk highly. A small k like 1 would make rank 1 worth twice rank 2.
- **Q: Keyword search alone scored lower than vector search. Why would fusing them help?** A: Because they fail on different questions. Keyword search ranks exact-term questions better, things like "C-LOOK", "setuid" or a number like 642, where the embedding blurs the exact word; on dev it ranked four questions higher than vector search did, even though its overall hit@5 was lower (0.818 vs 0.939). Fusion can keep those wins. But I measured it rather than assuming it: on my dev set, plain equal-weight fusion lowered hit@5 from 0.939 to 0.848. It fixed 3 questions and pushed 5 others down, mostly questions keyword search does not find at all. So hybrid is switched off by default, and I will test it again together with the reranker, which can re-order the combined candidates.
## Stage 2 Phase 1 step 10 - cross-encoder reranker (measured, not adopted)
- **Q: What is the difference between a bi-encoder and a cross-encoder?** A: The embedding model (bi-encoder) turns the question and each slide into separate vectors and compares them, so slide vectors can be computed once at ingest and search is fast. A cross-encoder reads the question and one slide together in a single transformer pass, so it can see which words actually answer the question; it is more precise but has to run once per (question, slide) pair at query time.
- **Q: Why rerank only 30 candidates?** A: Running the cross-encoder on all ~330 slides for every question would take tens of seconds on a laptop CPU. The fast retriever already has the answer in its top 10 for 32 of 33 dev questions, so reordering a short list is where a reranker could help.
- **Q: Why is it switched off?** A: I set the adoption rule before measuring: a dev gain and p95 under 1 s. On dev, hit@5 stayed 0.939, MRR dropped from 0.835 to 0.817 (it fixed one miss and created another), and p95 was 2.9 s. It failed both conditions, so the switch is off; the code and tests stay so it can be re-tested on other notes.
- **Q: Why might a model trained on MS MARCO not help here?** A: MS MARCO is web search questions over web paragraphs. My passages are short slide bullets with titles; the bi-encoder plus the "file > section" header already captures most of what the cross-encoder sees, and the reranker sometimes prefers a slide that repeats the question's words over the one that answers it (Q72).
- **Q: Couldn't you make it faster?** A: Yes (fewer candidates, shorter max length, ONNX), but there was no quality gain to pay for, so I did not spend time there. Speed only matters if the reranker improves ranking.
